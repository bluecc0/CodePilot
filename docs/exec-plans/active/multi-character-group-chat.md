## 用户问题与边界

用户希望把现有单一助理扩展成类似 SillyTavern 的角色库：支持多个助理/角色、导入主流角色卡，并让多个角色在同一会话中按批次或协作合同交谈。

本实现借鉴公开格式与用户可见行为，但独立实现数据模型和运行逻辑，不直接复制 SillyTavern 的 AGPL 源码。首版的安全默认是顺序批次：同一时刻只有一个角色执行，避免多个 Agent 并发写同一工作区。角色卡内容属于角色身份数据，不能覆盖 CodePilot 的权限、工具和 Runtime 规则。

## Phase 0：领域模型与导入

- 可导入 Character Card V1、V2、V3 的 JSON 和 PNG 卡片。

## Phase 2：顺序批次群聊

### 用户会看到什么

- 在群聊页发送一次，已启用角色按群组顺序逐个回复。
- 每条消息显示真实角色归属；刷新后仍能恢复角色名和批次顺序。
- 中途失败保留已完成回复，并把批次标为 partial/failed，不伪装全部完成。

### 本阶段明确不做什么

- 不复用上一个角色的 Runtime 会话状态；角色切换清空可恢复 Runtime ref，并从持久化群聊历史重建上下文。

- [x] `list`：全部启用成员按顺序发言。
- [ ] `manual`：用户点名一个或多个角色。
- [ ] `natural`：按点名、最近发言者和 talkativeness 选人，至少选择一个。
- [ ] `pooled`：优先选择本轮尚未发言的角色。
- [ ] 协作合同：目标、职责、轮次、停止条件、主持人和工具策略；所有字段有真实执行来源。

## 关键决策

- 角色身份与 Assistant workspace 分层：卡片是可移植角色描述，workspace 继续是用户拥有的文件、记忆与工具边界。
- 群聊采用一条 `chat_session`、多条带 speaker 归属的消息；不为每个角色伪造互不相干的聊天。
- 每个用户回合生成 durable `group_run`；客户端断开或某角色失败时仍可审计已完成序号。
- `group_run.next_index` 只能在冻结队列范围内单调前进；已 terminal 的 run 拒绝再次改写。
- 顺序执行是默认且首版唯一真实执行策略；“并行”不作为 UI 承诺。
