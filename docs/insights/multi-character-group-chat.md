# 多角色卡与群聊编排产品思考

> 技术实现见 [docs/handover/multi-character-group-chat.md](../handover/multi-character-group-chat.md)

## 用户真正要的不是“多个 system prompt”

角色卡只是可移植身份；群聊产品还必须回答三件事：谁在这一轮发言、每条回复到底属于谁、失败或刷新后如何恢复。如果只把多个 prompt 拼进一次模型调用，角色归属无法审计，模型也很容易替其他角色代写。

因此首版把 speaker、run 和 batch sequence 变成数据库事实，不从正文里的名字推断。一个用户回合对应一个 durable run；每位角色只写自己的回复。

## 为什么先做顺序批次

CodePilot 是能读写工作区和调用工具的 Agent 客户端，不是纯文字聊天室。多个角色同时运行会带来文件冲突、重复外部操作、权限请求归属混乱和 session lock 竞争。顺序批次虽然没有“并行蜂群”的表面速度，但它是首个可证明、可恢复、可停止的版本。

后续即使增加并行，也只能对声明为只读且无外部副作用的角色开放，不能把“模型可以同时生成文本”误当成“多个 Agent 可以安全并发”。

## 角色卡兼容的边界

兼容分三层：

1. 格式兼容：能读取 V1/V2/V3 JSON 和 PNG metadata。
2. 语义兼容：description、personality、scenario、greetings 等进入角色行为。
3. 扩展运行时兼容：Lorebook 扫描、正则脚本、assets、CHARX 等拥有完整执行语义。

当前交付覆盖前两层的核心字段，不声称第三层完整。扩展字段保留为 metadata 是为了未来迁移不丢数据，不代表已经执行其语义。

## Assistant workspace 与角色卡不能合并成同一个概念

Assistant workspace 是用户拥有的文件、记忆、工具和后台服务边界；角色卡是可导入、可分享、可替换的身份描述。把角色卡导入直接写进 `instructions.md/soul.md` 会污染用户真源，也让删除角色变成破坏性文件迁移。

因此角色卡独立落库，群聊时作为低于 CodePilot 安全规则的身份层注入。未来可以显式把某个角色绑定到一个 workspace，但必须是用户动作，不做隐式迁移。

## 删除群组不应该破坏历史

群组定义被 `group_runs` 和旧会话引用。硬删除要么失败，要么迫使应用级联删除可审计历史。这里的“删除”因此是从角色库中移除：写入 `deleted_at`，列表不再显示，但旧群聊仍能解析角色名称和队列。这比让一个整理按钮变成历史销毁器更符合用户预期。

## 隐私模式是视觉遮罩，不是认证

快速隐藏界面和密码锁是两种产品。当前隐私入口切换到不渲染会话列表、分屏、搜索、面板和通知 toast 的独立路由，并保留安全返回路径；它不声称能抵御拥有本机访问权的人。界面文案必须维持这个边界。

## 下一阶段优先级

1. 真实 Provider 两角色 smoke，验证 Claude/Native/Codex 的清 ref 与历史恢复边界。
2. 群组编辑、成员排序/启停和手动点名。
3. Natural/Pooled speaker selector 纯函数与可解释选择结果。
4. 协作合同状态机：职责、最大轮数、主持人、停止条件和工具策略。
5. 角色独立 Runtime lane 与长期记忆，再评估安全的只读并行。
